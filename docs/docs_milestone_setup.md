## How the Milestone Engine Works

**`ManualMilestoneService`** is now fully DB-driven. It reads from two tables:

```
milestone_definition  → what milestone types exist for a module (label, code, entity_type)
milestone_dependency  → which milestones must be completed BEFORE another can be recorded
```

When `recordMilestone()` is called, it:
1. Finds the `milestone_definition` row for `milestone_type`
2. Loads all `milestone_dependency` rows where `is_required = true`
3. Checks `manual_milestone` records to see if prerequisites are already recorded
4. Blocks recording if any required predecessor is missing
5. Persists the milestone and emits an Outbox event (`MILESTONE_RECORDED`) for SSE realtime broadcast

**Zero TypeScript changes needed — only DB inserts.**

## Milestones as Workflow Recommendation Targets

Manual Milestones serve as first-class checkable targets in the **Workflow Recommendation & Required Action Platform**.

### 1. Recommendation Target Binding
When a user recommends or requires a milestone during a `FORWARD` or `RETURN` action:
```json
{
  "target_type": "MILESTONE",
  "target_code": "SECTION_4_NOTIFICATION",
  "isRequired": true,
  "requiredBeforeTransitionId": "forward_to_pccf"
}
```

### 2. Batch Fulfillment Resolution
The `WorkflowTargetResolverRegistry.resolveTargetFulfillmentBatch()` queries `manual_milestone` records in batch by entity ID & `milestone_type`. If a matching milestone is present, the recommendation status dynamically resolves to `FULFILLED`.

### 3. Transition Unblocking & Realtime Sync
Recording the required milestone satisfies `RequiredRecommendationsFulfilledGuard` for downstream workflow transitions. An Outbox event triggers SSE realtime stream updates to automatically refresh `<WorkflowTimelineFeed />` and `<ManualMilestonePanel />` without page reload.

## Filtering `milestone_definition` by Acquisition Mode (CBA Act vs RFCTLARR)

In the `LAND_SCHEDULE` module, land acquisition can occur under different legal modes (e.g., **CBA Act**, **RFCTLARR Act**, **Direct Purchase**).

To filter milestone definitions by Acquisition Mode:

### 1. `module_code` Naming Convention
Set `module_code` in `milestone_definition` to the mode-suffixed workflow code generated by `resolveWorkflowCode(MODULE_CODES.LAND_SCHEDULE, acqModeId)`:

| Acquisition Mode | `module_code` in `milestone_definition` | Examples of Statutory Milestones |
|---|---|---|
| **CBA Act** (`acq_mode = 1`) | `LAND_SCHEDULE_CBA_ACT` (or `LAND_SCHEDULE_1`) | `SECTION_4_NOTIFICATION`, `SECTION_7_NOTIFICATION`, `SECTION_9_NOTIFICATION`, `SECTION_11_DECLARATION` |
| **RFCTLARR Act** (`acq_mode = 2`) | `LAND_SCHEDULE_RFCTLARR` (or `LAND_SCHEDULE_2`) | `SIA_NOTIFICATION`, `SECTION_11_PRELIMINARY`, `SECTION_19_DECLARATION`, `SECTION_23_AWARD` |
| **Universal / All Modes** | `LAND_SCHEDULE` | `FORM_XXII_ISSUE`, `OTHER_MILESTONE` |

### 2. Automatic Array Filtering & Fallback
`ManualMilestoneService.getDefinitionsForModule()` automatically parses mode-suffixed codes. Calling:
```http
GET /api/milestones/definitions?moduleCode=LAND_SCHEDULE_CBA_ACT&entityType=acq_land_schedule
```
queries `where: { module_code: { in: ['LAND_SCHEDULE_CBA_ACT', 'LAND_SCHEDULE'] } }`.

This seamlessly returns **BOTH** the mode-specific statutory milestones (CBA Section 4/7/9/11) **AND** universal milestones (`LAND_SCHEDULE`) in one clean query!

## The Two Tables

### `public.milestone_definition`

| Column | Type | Description |
|---|---|---|
| `module_code` | `VARCHAR(60)` | Must equal `MODULE_CODES.YOUR_MODULE` — used by `getDefinitionsForModule()` |
| `milestone_code` | `VARCHAR(80)` | Machine name — unique per module. Stored in `manual_milestone.milestone_type` |
| `name` | `VARCHAR(120)` | Human-readable label shown in `ManualMilestonePanel` dropdown |
| `description` | `TEXT` | Tooltip / help text |
| `entity_type` | `VARCHAR(64)` | Must equal `CHECKABLE_ENTITY_TYPES.X` — used in `manual_milestone` rows |
| `metadata_schema` | `Json` | Optional JSON Schema for extra fields (authority, reference_no validation) |
| `is_active` | `BOOLEAN` | Set `false` to soft-delete |

### `public.milestone_dependency`

| Column | Type | Description |
|---|---|---|
| `milestone_id` | `UUID` | FK → `milestone_definition.id` — the milestone being recorded |
| `required_milestone_id` | `UUID` | FK → `milestone_definition.id` — the prerequisite that must exist first |
| `condition_type` | `VARCHAR(30)` | `'REQUIRED'` (blocks) or `'RECOMMENDED'` (warns, doesn't block) |
| `is_required` | `BOOLEAN` | `true` = hard block. `false` = soft warning only |

## Step 0 — Ensure Module Code is Registered

The `entity_type` stored in `manual_milestone` must use `CHECKABLE_ENTITY_TYPES.X`.

```ts
// src/core/config/module-codes.config.ts

// If FOREST_CLEARANCE is new, add BOTH:
export const MODULE_CODES = {
  // ...existing...
  FOREST_CLEARANCE: 'FOREST_CLEARANCE',   // ← add this
} as const

export const CHECKABLE_ENTITY_TYPES = {
  // ...existing...
  FOREST_CLEARANCE: 'forest_clearance',   // ← add this (lowercase, used as entity_type in DB)
} as const
```

> [!CAUTION]
> The `entity_type` stored in `manual_milestone` MUST be `CHECKABLE_ENTITY_TYPES.FOREST_CLEARANCE`
> (`'forest_clearance'`), NOT `MODULE_CODES.FOREST_CLEARANCE` (`'FOREST_CLEARANCE'`).
> These are two different constants for two different purposes.

## Step 2 — Insert Milestone Dependencies (Conditions)

```sql
-- Step 2: Wire up the prerequisite chain

INSERT INTO public.milestone_dependency
  (milestone_id, required_milestone_id, condition_type, is_required, entryby)
VALUES

  -- Section 7 REQUIRES Section 4 (hard block)
  ('11111111-0000-0000-0000-000000000002',  -- milestone_id: Section 7
   '11111111-0000-0000-0000-000000000001',  -- required_milestone_id: Section 4
   'REQUIRED', true, 'system'),

  -- Section 9 REQUIRES Section 7 (hard block)
  ('11111111-0000-0000-0000-000000000003',  -- milestone_id: Section 9
   '11111111-0000-0000-0000-000000000002',  -- required_milestone_id: Section 7
   'REQUIRED', true, 'system'),

  -- Section 11 REQUIRES Section 9 (hard block)
  ('11111111-0000-0000-0000-000000000004',  -- milestone_id: Section 11
   '11111111-0000-0000-0000-000000000003',  -- required_milestone_id: Section 9
   'REQUIRED', true, 'system'),

  -- Form-XXII RECOMMENDS Section 4 (soft warning — does NOT block)
  ('11111111-0000-0000-0000-000000000005',  -- milestone_id: Form-XXII
   '11111111-0000-0000-0000-000000000001',  -- required_milestone_id: Section 4
   'RECOMMENDED', false, 'system');         -- is_required=false → warning only, not a hard block
```

### Resulting dependency graph:

```
Section 4  ──(required)──▶  Section 7  ──(required)──▶  Section 9  ──(required)──▶  Section 11
Section 4  ──(recommended)──▶  Form-XXII  (soft warning, not blocked)
OTHER_MILESTONE  ── (no deps, always available)
```

## Step 4 — How the UI Loads Milestone Types

The `ManualMilestonePanel` component must call the definitions API (not import `milestoneConfig`):

```ts
// In your module's component:
const { data } = useQuery({
  queryKey: ['milestone-definitions', MODULE_CODES.FOREST_CLEARANCE],
  queryFn: async () => {
    const r = await fetch(
      `/api/milestones/definitions?moduleCode=${MODULE_CODES.FOREST_CLEARANCE}&entityType=${CHECKABLE_ENTITY_TYPES.FOREST_CLEARANCE}`
    )
    return r.json()
  }
})

// data.definitions = [{ id, label, requires: ['DFO_INSPECTION'], ... }]
```

Pass to `ManualMilestonePanel`:
```tsx
<ManualMilestonePanel
  config={data?.definitions ?? []}
  entityType={CHECKABLE_ENTITY_TYPES.FOREST_CLEARANCE}
  entityId={record.id}
  // ...
/>
```

## Conditional Milestone Patterns

### Pattern A: Hard sequential chain (most common)
Each milestone blocks the next. Use `is_required = true`.

```
A → B → C → D
Each row in milestone_dependency: milestone_id=B, required=A; milestone_id=C, required=B; etc.
```

### Pattern B: Multiple prerequisites (AND logic)
A milestone requires BOTH X and Y before it can be recorded:

```sql
-- Stage-II requires BOTH Wildlife NOC AND CA Plan (two rows, same milestone_id)
INSERT INTO milestone_dependency (milestone_id, required_milestone_id, is_required)
VALUES
  ('stage-ii-id', 'wildlife-noc-id', true),
  ('stage-ii-id', 'ca-plan-id', true);
```

### Pattern C: Soft recommendation (OR warning)
Use `is_required = false`, `condition_type = 'RECOMMENDED'`.
The milestone can still be recorded — the service logs a warning but does not block.

### Pattern D: Independent milestones (no prerequisites)
Simply do NOT insert any row in `milestone_dependency` for that milestone.
`OTHER_MILESTONE` is always independent by design.

## Verification Checklist

After inserting:

- [ ] `milestone_definition.module_code` matches `MODULE_CODES.X` exactly (case-sensitive)
- [ ] `milestone_definition.entity_type` matches `CHECKABLE_ENTITY_TYPES.X` exactly (lowercase)
- [ ] All `milestone_dependency` foreign keys reference valid `milestone_definition.id` UUIDs
- [ ] Dependency graph has no cycles (A→B→C, never C→A)
- [ ] Run:
  ```sql
  SELECT md.milestone_code, md.name, dep.required_milestone_id, req.milestone_code AS requires
  FROM public.milestone_definition md
  LEFT JOIN public.milestone_dependency dep ON dep.milestone_id = md.id
  LEFT JOIN public.milestone_definition req ON req.id = dep.required_milestone_id
  WHERE md.module_code = 'FOREST_CLEARANCE'
  ORDER BY md.milestone_code;
  ```
